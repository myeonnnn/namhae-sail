# 기능을 만드는 순서

요청: $ARGUMENTS

## 1. 수용 기준

요청을 확인할 수 있는 문장으로 정리해서 `docs/spec.md`의 해당 절에 추가한다. 기존 문장과 어긋나면 어느 쪽을 따를지 사용자에게 묻는다.
여러 파일에 걸치거나 동작이 바뀌는 기능이면 추가한 문장을 보여 주고 확인을 받는다.
눈으로 판단해야 하는 기준(물거품의 모양, 움직임)은 **[화면]**으로 표시하고, 테스트로 옮기지 않는다.

## 2. 테스트 작성

`test-writer` 에이전트에게 맡긴다. 전달하는 것은 요청 원문, `docs/spec.md`에서 확인된 문장, 건드릴 모듈의 경로와 시그니처뿐이다. 구현 계획과 구현 코드는 전달하지 않는다.
새 함수라면 시그니처와 JSDoc만 있고 몸통은 `throw new Error('아직 구현하지 않았다')`인 파일을 먼저 만들어 둔다. 그래야 테스트가 import 오류가 아니라 기능이 없어서 실패한다.

## 3. 실패 확인

새 테스트가 올바른 이유로 실패하는지 직접 실행해서 확인한다. 실패 이유별 개수를 센다. 이 단계 전에는 구현을 시작하지 않는다.

## 4. 구현

테스트가 통과할 때까지 구현한다. 테스트는 고치지 않는다 (훅이 막는다). 테스트가 틀렸다고 판단되면 이유를 사용자에게 보고하고, 수정은 `test-writer`에게 맡긴다.

## 5. 확인

`pnpm typecheck`와 `pnpm test`를 통과시킨다. 화면에 보이는 변경이면 브라우저에서 확인한다.
수식, 좌표, 판정 기준을 바꾼 변경이면 그 지점을 `scripts/harness/faults.mjs`에 추가할지 사용자에게 제안한다.

## 6. 보고

통과한 테스트의 출력, 실패에서 통과로 바뀐 개수 같은 증거를 붙이고, 확인하지 못한 것은 따로 밝힌다.
